# Architecture Review — 2026-03-01

> Full codebase review across 4 axes: concurrency, algorithmic edge cases, system boundaries, and testing gaps.
> Includes Gemini's architectural evolution recommendations.

## Stack-Ranked Findings

Ordered by blast radius × likelihood. Each entry has the failure mechanism, exact location, and fix.

## CRITICAL

### C1. Agent.SetGraph() data race — agent clicks wrong element or segfaults

**Mechanism:** `SetGraph` writes `a.fs`, `a.lsTool.fs`, `a.catTool.fs`, `a.actTool.fs` (6 pointer stores) without holding `a.mu`. Concurrently, `HandleIntent` reads `a.fs` to execute tool calls. If the Doer calls `SetGraph` (`doer.go:336,369`) while the Navigator is mid-tool-chain, the agent reads a half-swapped fs — e.g., `lsTool` sees the new graph but `actTool` still sees the old one. An `act /main/stories/_c/3` resolves `mache-27` in the old graph, but the new graph has renumbered it to `mache-14`. The agent clicks the wrong element.

**Location:** `internal/navigator/agent.go:103-111` (write), `agent.go:159,184,272` (read)

**Fix:** Acquire `a.mu.Lock()` inside `SetGraph`, use `a.mu.RLock()` around the entire tool-dispatch in `HandleIntent`. Or — simpler — make `fs` an `atomic.Pointer[NavFS]` and swap atomically, then each tool call captures the pointer once at entry.

### C2. sess.CVRegions unsynchronized read/write — stale region data sent to extension

**Mechanism:** `handleDOMSnapshot` (goroutine A) writes `sess.CVRegions` at `snapshot.go:148`. `SendActionToExtension` (goroutine B, from Doer) reads `sess.CVRegions` at `websocket.go:627`. No lock protects this field. Under `-race`, this is a flagged data race. Under real execution, the Doer can read a partially-written slice header (pointer + length mismatch), causing either a panic or sending stale/corrupt region coordinates to the extension.

**Location:** `internal/api/snapshot.go:148-152` (write), `internal/api/websocket.go:627` (read)

**Fix:** Add `CVRegions` access to `schemaMu`, or use `atomic.Value` with a frozen `[]CVRegion` slice.

---

### C3. sess.RescanPath unsynchronized read/write — targeted rescan fires on wrong path

**Mechanism:** The Doer writes `sess.RescanPath = action.Path` (`doer.go:354`). `handleDOMSnapshot` reads and consumes it (`snapshot.go:101-103`). These run in different goroutines with no lock. Race outcome: the rescan path is either empty (consumed too early) or stale (from a previous rescan). Either way, the Cartographer generates a schema for the wrong subtree.

**Location:** `internal/api/doer.go:354` (write), `internal/api/snapshot.go:101-103` (read)

**Fix:** Route `RescanPath` through `schemaMu` or pass it via the `InboundMessage` struct (embed it in the WebSocket message rather than shared state).

---

### C4. sess.CurrentURL unprotected read/write in Doer — goto skipped or double-fired

**Mechanism:** `doer.go:315` reads `d.sess.CurrentURL` without `schemaMu` to decide whether to skip navigation. `doer.go:326` writes it without lock. Meanwhile, `snapshot.go:245-250` and `session.go:SetCurrentURL` write it under `schemaMu`. If a snapshot completes at the exact moment the Doer reads `CurrentURL`, the comparison is against a torn read. The Doer either skips a necessary navigation (thinks it's already there) or double-navigates (thinks it's somewhere else).

**Location:** `internal/api/doer.go:315,326`

**Fix:** Use `d.sess.GetCurrentURL()` and `d.sess.SetCurrentURL()` which hold `schemaMu`. Two-line fix.

---

### C5. Planner passes req.TabID instead of resolved tabID — operates on wrong tab

**Mechanism:** `HandleAgentTask` resolves the actual tab via `h.resolveTab()` at `planner.go:409`, storing result in local `tabID`. But line 431 passes `req.TabID` (the original, potentially-zero request value) to `RunTask`. If `resolveTab` redirected to an existing tab, the Planner runs its multi-turn Gemini loop against the wrong tab.

**Location:** `internal/api/planner.go:431`

**Fix:** Change `req.TabID` to `tabID` on line 431.

## HIGH

### H1. Unbounded goroutine spawning per DOM_SNAPSHOT — OOM / API bill explosion

**Mechanism:** Every `DOM_SNAPSHOT` message spawns `go h.handleDOMSnapshot(conn, msg)` (`websocket.go:254`) with no semaphore. Each goroutine decodes a base64 screenshot (~5-15 MB), runs edge detection (~85 MB transient for 1080p), and potentially calls the Gemini API. A misbehaving extension (or attacker on the open WebSocket) can send hundreds of snapshots, spawning hundreds of goroutines that each allocate ~100 MB and make API calls.

**Location:** `internal/api/websocket.go:254-255`

**Fix:** Add a `chan struct{}` semaphore (capacity 2-3) around snapshot processing. Drain excess messages or reject with backpressure.

---

### H2. WebSocket upgrader CheckOrigin: true — cross-site WebSocket hijacking

**Mechanism:** Any website the user visits can open `ws://localhost:8080/ws` and inject `DOM_SNAPSHOT`, `NAVIGATE`, or `DOER_SUBMIT` messages. Since the system can execute browser actions (clicks, typing, navigation), this is a full browser takeover from any malicious webpage.

**Location:** `internal/api/websocket.go:31-33`

**Fix:** Restrict `CheckOrigin` to the extension's origin (`chrome-extension://<id>`) or a shared secret header.

---

### H3. No image dimension/size limit — pixel bomb OOM

**Mechanism:** `image.Decode(bytes.NewReader(screenshotBytes))` at `snapshot.go:130` has no dimension guard. A crafted 65535x65535 PNG (small compressed, enormous decompressed) allocates ~16 GB on decode. The base64 decode at `snapshot.go:114` similarly has no size limit.

**Location:** `internal/api/snapshot.go:114,130`, `internal/api/edges.go:38`, `internal/mache/crop.go:20`

**Fix:** Wrap in `image.DecodeConfig` first to check dimensions, reject anything above a sane limit (e.g., 4096x4096). Use `io.LimitReader` on the base64 input.

---

### H4. handleDOMSnapshot goroutines orphaned on disconnect — wasted API calls, goroutine leak

**Mechanism:** Both `handleDOMSnapshot` and `handleNavigate` use `context.Background()` (`snapshot.go:19`, `websocket.go:284`). When the WebSocket disconnects, these goroutines continue running until the Cartographer/Gemini call completes (potentially 30+ seconds). The results are discarded, but the API cost is paid and goroutines accumulate.

**Location:** `internal/api/snapshot.go:19`, `internal/api/websocket.go:284`

**Fix:** Derive context from a per-connection `context.WithCancel`. Cancel it in the WebSocket disconnect cleanup path.

---

### H5. SchemaCache.persistLocked() holds write lock during SQLite I/O — reader starvation

**Mechanism:** `Put`, `PutZones`, `InvalidateZone`, `PutZone` all call `persistLocked()` under `c.mu.Lock()`. `persistLocked` calls `graph.ExportSQLite()` which does disk I/O. All concurrent readers (`Get`, `GetAllZones`) block for the duration of the write. On slow storage or large graphs, this creates latency spikes in the pipeline.

**Location:** `internal/api/schemacache.go:111-137,159-230,292,306,346`

**Fix:** Copy the graph snapshot under lock, release lock, then write to SQLite outside the critical section. Or use a write-ahead log pattern (write to new file, atomic rename).

---

### H6. Non-atomic InvalidateZone + PutZone in partial regen — concurrent reader sees empty cache

**Mechanism:** `attemptPartialRegen` (`partial.go:152-158`) calls `InvalidateZone(key, path)` then `PutZone(key, m)` for each zone. Between these two calls, a concurrent `Get(key)` from another snapshot goroutine sees the zone as missing. It concludes "cache miss" and triggers a full Cartographer call unnecessarily, or worse, returns an incomplete schema.

**Location:** `internal/api/partial.go:152-158`

**Fix:** Add a `PutZoneAtomic(key, path, mount)` that does invalidate+put inside a single lock acquisition. Or batch all zone updates into a single `PutZones` call.

---

### H7. H⁰ folding can violate minZones contract — schema collapses to 1 zone

**Mechanism:** `cutTree` enforces `minZones` (3-7 range) at `tropical.go:838-850`. But `foldCoherentZones` runs after `cutTree` (line 182) and can merge zones below the minimum. If tolerance is aggressive and zones have similar fiber signatures, 4 zones become 1. Downstream: the VFS has a single mount, the agent sees no structural hierarchy, navigation degrades to "click anything."

**Location:** `internal/cartographer/tropical.go:167-183` (ordering), `tropical.go:838-850` (enforcement)

**Fix:** Add a post-folding guard: `if len(zones) < minZ { return pre-fold zones }`. Or integrate the minZones constraint into the folding algorithm.

---

### H8. No HTTP server timeouts — slowloris / connection exhaustion

**Mechanism:** `http.Server{Addr: port}` at `main.go:172` has zero timeout configuration. A slowloris attacker holds connections open indefinitely. `HandleAgentTask` blocks for the entire Planner loop (up to 15 Gemini turns, minutes).

**Location:** `cmd/agentd/main.go:172`

**Fix:** Set `ReadTimeout: 30s`, `WriteTimeout: 5m` (generous for Planner), `IdleTimeout: 120s`.

---

### H9. Session map never GC'd on extension crash — unbounded memory growth

**Mechanism:** `h.sessions` only shrinks via `handleTabClosed` (`websocket.go:354`), which requires the extension to send `TAB_CLOSED`. An extension crash orphans all sessions — each holding an `Engine` (in-memory graph), `Navigator`, channels, and a running `Doer` goroutine. Over hours of development with repeated extension reloads, memory grows monotonically.

**Location:** `internal/api/websocket.go:196-204`

**Fix:** On WebSocket reconnect, diff the live tab list against `h.sessions` and reap orphans. Or add a session TTL with periodic sweep.

---

### H10. Unbounded io.ReadAll on LLM responses — OOM from local model

**Mechanism:** `io.ReadAll(resp.Body)` at `model.go:84,339` and `ollama.go:86` reads the entire response body with no limit. A misconfigured or malicious local LLM returning a massive response causes OOM.

**Location:** `internal/navigator/model.go:84,339`, `internal/cartographer/ollama.go:86`

**Fix:** `io.LimitReader(resp.Body, 10*1024*1024)` — 10 MB is generous for any LLM response.

## SUBTLE

### S1. Prefilter drops structural container nodes — tree degrades for complex pages

**Mechanism:** `prefilterElements` (`tropical.go:222-259`) prioritizes elements with text, then color, then "rest". Container nodes (`<body>`, `<main>`, `<nav>`, `<section>`) typically have neither text nor color — they land in the lowest-priority `rest` bucket. On a page with 500+ text elements, all containers are dropped. The NJ tree loses its structural hierarchy roots, producing a flat topology where the structural fiber contributes no useful signal.

**Location:** `internal/cartographer/tropical.go:229-238,255-258`

**Fix:** Add a 4th priority tier for "structural containers" (elements matching `body`, `main`, `nav`, `header`, `footer`, `section`, `article`, `aside`, `form`) that reserves 20-30 slots from the 500 budget before filling text/color.

---

### S2. Prefilter truncation has positional bias — late-DOM content dropped

**Mechanism:** When `withText` alone exceeds 500, the truncation at `tropical.go:256` is `result[:maxN]` — document order. Elements appearing later in the DOM (main content area, footer) are systematically dropped while header/nav elements survive. On long pages (e-commerce product lists, news feeds), this means the agent literally cannot see the bottom half of the page.

**Location:** `internal/cartographer/tropical.go:255-258`

**Fix:** Score elements by a composite of spatial spread + text length + interactivity, then take the top-500 by score. Or use reservoir sampling for unbiased selection.

---

### S3. Alpha channel silently discarded in RGB sampling — transparent regions poison visual fiber

**Mechanism:** `sampleRGB` at `tropical.go:419` calls `img.At(sx,sy).RGBA()` and discards alpha. Go returns pre-multiplied values, so transparent pixels read as `(0,0,0)` regardless of actual color. Two elements on transparent regions cluster together (visual distance = 0) even if structurally unrelated. Currently unreachable with CDP screenshots (always opaque PNG), but a time bomb if the pipeline ever accepts composited images.

**Location:** `internal/cartographer/tropical.go:419`

**Fix:** Check alpha; if zero, fall back to neutral visual distance (0.5) same as the "no RGB" path.

---

### S4. Agent multi-step tool chain sees inconsistent VFS during DOM mutation

**Mechanism:** The Navigator executes `ls -> cat -> act` as separate tool calls against the Engine. Between steps, `handleDOMSnapshot` can `SwapEngine` (via `doer.go:329`), replacing the graph. `ls` returns children from schema v1; `act` resolves against schema v2. The ordinal `_c/3` now points to a different element. The `Engine.mu` RWMutex ensures no panic, but semantic correctness is not guaranteed.

**Location:** Architectural — spans `navigator/agent.go:159-272` (tool dispatch) and `api/doer.go:328-336` (engine swap)

**Fix:** Snapshot the `NavFS` at the start of each `HandleIntent` call and use that frozen snapshot for all tool calls within that turn. The `SetGraph` atomicity fix from C1 partially addresses this — capture the pointer once.

---

### S5. Bridge.Act() uses context.Background() — hangs forever if iTerm2 unresponsive

**Mechanism:** `Bridge.Act()` at `bridge.go:318` creates `context.Background()` for the iTerm2 RPC call. If the iTerm2 Unix socket hangs (process frozen, socket buffered), the goroutine blocks on `send()` indefinitely. No timeout, no circuit breaker.

**Location:** `internal/iterm/bridge.go:318`

**Fix:** `context.WithTimeout(ctx, 5*time.Second)`.

## Algorithmic Edge Cases (Confirmed Safe)

The following were investigated and found to be properly guarded:

| Area | Finding |
|------|---------|
| All fiber distance divisions | Every denominator is either a constant, guarded by > 0 check, or prevented from being zero by structural invariants |
| NaN propagation | Every fiber returns a neutral constant (0, 0.5) when data is missing |
| NJ with N=0,1,2,3 | All explicitly special-cased |
| NJ (m-2) denominator | Loop guard `len(active) > 2` ensures m >= 3; explicit `m > 2` check before division |

| NJ degenerate metric | Produces valid caterpillar tree, deterministic (lexicographic tie-break) |

| FFT Hann window | `n <= 1` guard prevents `n-1 = 0` division |
| FFT variance underflow | Explicit `variance < 0 -> 0` guard |

| Union-find races | Single-threaded, no goroutines |
| Coincident bbox centers | Other fibers still contribute via max-plus |

## V2 Architecture Evolution (Post-Hackathon)

### The Problem

The current architecture has `Handler`, `TabSession`, `Engine`, `SchemaCache`, `Agent`, and `Doer` all running in concurrent goroutines, all reading/writing the same shared pointers via `sync.RWMutex`. As surface area grows, this "Shared-Memory Concurrency" pattern doesn't scale — lock hierarchy becomes impossible to hold in your head.

### Option 1: MVCC for the Graph

Make the graph **immutable**. When a DOM update arrives, the Cartographer builds a brand new graph in memory. Use `atomic.Pointer` to swap the active graph pointer instantly. If the LLM is mid-reasoning-loop, it holds a reference to Graph v1 safely — Graph v1 never changes. When the LLM finishes, it grabs the latest pointer (Graph v2). Zero mutexes, zero races, infinite read scalability.

### Option 2: Actor Model for State

Turn `TabSession` into an "Actor" — the session owns its state completely, no other goroutine touches it. Give it a single `updates chan Event`. The Doer, WebSocket handler, and Snapshotter send events instead of writing fields directly. The session processes events in a single `for { select {} }` loop. State updates become perfectly serialized. All mutexes deleted.

### Option 3: Merkle DAG (Content-Addressed VFS)

Every node's ID is a hash of its contents + children's hashes. DOM mutation produces a new root hash; everything else is structurally shared. The `zone.Fingerprint` in `tropical.go` already computes content-addressed hashes per zone — just need to bubble them up to a true Merkle root. Eliminates cache invalidation entirely (old hashes just stop being referenced). Targeted diffing in O(log N).

### Option 4: Just Use mache's SQLite Backend

mache already has `SQLiteGraph` (`internal/graph/sqlite_graph.go`) and CAS overlays (ADR-0003). x-ray's in-memory `MemoryStore` is a hand-rolled DB with hand-rolled locking. SQLite with WAL mode gives native MVCC: one writer, unlimited concurrent readers, zero torn reads. The agent reads the mounted FUSE/NFS filesystem — the OS kernel handles concurrency. The latency difference (50ns vs 50μs) is invisible to an LLM agent that waits 1-3 seconds for Gemini.

## Mache Gap Analysis (What's Duplicated vs. What's Not)

### The honest verdict: you're NOT duplicating mache

x-ray uses mache correctly as a graph library. The x-ray `Engine` adds DOM-specific logic (zones, ordinal children, CSS selectors, bounds validation) that doesn't belong in mache. The "reinvention" is narrower than initially assumed.

### What x-ray already uses from mache correctly

| Capability | Mache | X-Ray |
|------------|-------|-------|
| In-memory graph store | `graph.NewMemoryStore()` | Used directly as backing store |
| Graph traversal API | `graph.Graph` interface | Engine wraps it with zone/child logic |
| Prefix-based multiplexing | `CompositeGraph` | Already using correctly |
| SQLite persistence | `ExportSQLite/ImportSQLite` | SchemaCache uses correctly |

### What x-ray is NOT using from mache

| Capability | Mache | X-Ray |
|------------|-------|-------|
| **Thread-safe graph pointer swap** | **`HotSwapGraph` (`hotswap.go`)** | **Hand-rolled `engineMu` + `SwapEngine`** |
| FUSE/NFS filesystem projection | Full implementation (1481 LOC) | Not used |
| Write-back + tree-sitter validation | Full pipeline | Not used |

### The one thing actually reinvented: HotSwapGraph

`HotSwapGraph` is the exact fix for C1 (the `Agent.SetGraph` race). x-ray wrote `TabSession.engineMu + SwapEngine` to protect the `Engine` pointer — but then `Agent.SetGraph` bypasses it entirely by directly writing `a.fs` without any lock. Meanwhile, mache's `HotSwapGraph` wraps any `graph.Graph` with per-call `RLock`/`Swap`-`Lock`, which is exactly the needed pattern.

If the Navigator's graph were a `*graph.HotSwapGraph` instead of a raw `graph.Graph`:
- Call `hotswap.Swap(newEngine)` instead of `agent.SetGraph(newFS)`
- Every `ls`/`cat`/`act` tool call gets an `RLock` per operation automatically
- No data race possible — the old graph stays valid for in-flight readers

### Why FUSE/NFS is wrong for this use case

The Navigator agent doesn't do `os.ReadDir()` — it calls `engine.ListDir()` and `engine.ReadFile()` through Go interfaces. Going through FUSE/NFS would add:
- Kernel round-trips (~50-200μs per call on macOS)
- Serialization/deserialization of node data
- Mount lifecycle management per tab (mount/unmount on navigation)

For an LLM that takes 1-3s per turn, this latency is invisible. But the **complexity** of managing per-tab FUSE mounts (OS-level failure modes, sudo requirements, macOS `diskutil` quirks) far exceeds the complexity of the mutex bugs. The in-memory `graph.Graph` interface is the right abstraction.

### Why SQLite WAL is impractical here

The graph is **ephemeral** — rebuilt from scratch on every DOM snapshot (every page load, every rescan). SQLite export is for cache persistence across sessions, not for live serving. Swapping to `SQLiteGraph` as the live backing store means:
- Serializing every `AddNode` call to disk (hundreds of nodes per schema)
- SQL query overhead on every `ls`/`cat` operation
- No meaningful MVCC benefit because the graph is replaced wholesale, not incrementally mutated

## The Actual Fix Plan

### Category A: Pointer-swap races (C1-C5)

All the same pattern: shared pointer/value read and written from different goroutines without synchronization.

1. **C1:** Wrap the `CompositeGraph` in `graph.NewHotSwapGraph()` before passing to Navigator. Delete `Agent.SetGraph()` — call `hotswap.Swap()` instead.
2. **C4:** Change `doer.go:315,326` to use `sess.GetCurrentURL()` / `sess.SetCurrentURL()`. Two lines.
3. **C3:** Route `RescanPath` through the `InboundMessage` (pass via WebSocket message, not shared state).
4. **C2:** Protect `CVRegions` with `schemaMu` or `atomic.Value`.
5. **C5:** Change `planner.go:431` from `req.TabID` to `tabID`. One word.

### Category B: Missing backpressure and lifecycle (H1, H4, H8, H9)

Infrastructure-level, not abstraction-level. Independent fixes:
- Semaphore on snapshot goroutines (H1)
- Per-connection context cancellation (H4)
- Server timeouts (H8)
- Session reaping on reconnect (H9)

### Hackathon Plan

Apply Category A fixes (quick wins, eliminate all CRITICAL data races). Category B and V2 architecture documented for post-hackathon.
